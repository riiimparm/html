SBOM最小要素:2021年版→2026年版で何が変わったか

2026年7月29日、CISA(米国土安全保障省サイバーセキュリティ・インフラセキュリティ庁)がNSA・FBI・G7各国機関を含む18機関共著で 「2026 Minimum Elements for a Software Bill of Materials (SBOM)」を正式発行しました。 これは2021年にNTIA(米国家電気通信情報庁)が定めた「SBOM最小要素」を全面的に更新・置き換えるものです。

① 背景:なぜ今、改訂されたのか

  • 2021年版の限界:当時はSBOM導入がまだ黎明期で、要素定義は「入門的」なものにとどまっていた。
  • 導入の急拡大とツールの成熟:2021年以降、SBOMの生成・共有・分析を行う組織が急増し、ツールの機能も大幅に進化。これにより発注側が「もっと詳しい情報」を要求できるようになった。
  • 国際的な広がり:EUサイバーレジリエンス法(SBOM提出を義務化)、ドイツBSIの技術要件、日本の経産省ガイダンス、インドCERT-Inの指針など、各国・地域で独自のSBOM要件が整備され、国際的な足並みを揃える必要が出てきた。
  • 手続きの経緯:2025年8月に「2025年版ドラフト」としてパブリックコメントを募集(〜2025年10月3日)。寄せられた意見を反映し、2026年7月29日に最終版として発行された。
つまり今回の改訂は、単なる思いつきの変更ではなく「4年間の実運用で見えた曖昧さ・不足を、業界からのフィードバックを基に埋める」作業です。2021年版の理念(自動化重視など)は維持されています。

② 新規追加されたデータフィールド(New)

2021年版には存在しなかった、まったく新しい10個のフィールドです。目的は「より詳細でリスク判断に使える情報」の追加です。

フィールド名内容追加理由
Component Hash Value新規コンポーネント実行ファイルのハッシュ値改ざん検知・完全性検証のため
Component Hash Algorithm新規ハッシュ計算に使ったアルゴリズムハッシュ値だけでは検証できないため、アルゴリズムの明記が必須
Component License新規コンポーネントのライセンス識別子ライセンス違反・著作権リスクの管理のため
SBOM Author Signature新規SBOM作成者のデジタル署名SBOM自体の真正性・改ざん防止(検証可能性)のため
SBOM Data Format Name新規使用しているSBOMデータ形式名(SPDX/CycloneDXなど)ツールがSBOMを正しく読み込めるようにするため
SBOM Data Format Version新規データ形式のバージョン非推奨バージョンの混在を避けるため
SBOM Generation Context新規SBOM生成時のソフトウェアライフサイクル段階(ビルド前/中/後 等)同じコンポーネントでも生成タイミングで内容が変わるため、文脈情報が必要
SBOM Tool Name新規SBOM生成に使ったツール名ツール由来の誤差・品質差を追跡可能にするため
SBOM Tool Version新規ツールのバージョン同上
SBOM Version新規SBOM文書自体のバージョン(セマンティックバージョニング推奨)同じコンポーネントに対し複数版のSBOMが存在しうるため、履歴管理が必要

③ 定義が大きく変わったフィールド(Major Update)

フィールド名変更内容
SBOM Author大幅更新旧「Author of SBOM Data」から改称。SBOM生成ツールではなく「ツールを操作した組織・人」を指すことを明確化。Component Producerとの違いも明記。
Component Identifiers大幅更新旧「Other Unique Identifiers」から改称。CPE・PURL等の共通識別子を最低1つ必須とし、UUID・コミットハッシュ・OmniBOR/SWHIDなども許容。
Component Producer大幅更新旧「Supplier Name」を置き換え。「サプライヤー」という語が流通業者との混同を招いていたため、「コンポーネントを作った実体」を指す語に変更。不明な場合は「provenance不明」と明記する運用も追加。
Component Version大幅更新旧「Version of the Component」を改称。バージョン不明の場合は「unknown」と明記することを新たに規定。

加えて、実務プロセス(Practices and Processes)側にも大幅更新があります:

  • Coverage(旧Depth):「深さ」から「網羅性(水平方向も含む)」の概念に変更。トップレベル依存だけでなく推移的依存も対象に。
  • Explicitly Identifying Unknown Information(旧Known Unknowns):「不明」と「意図的な非開示」を区別することを明確化。
  • Accommodation of Updates to SBOM Data(旧Accommodation of Mistakes):ツール成熟によりSBOMデータの正確性が上がったことを反映し定義を見直し。
  • Machine-Processable Data(旧Automation Support):SWIDタグを削除し、SPDX/CycloneDXなど実際に広く使われる形式に絞った。

④ 表現・記述が調整された既存フィールド(Minor Update)

フィールド名変更内容
SBOM TimestampRFC 9557準拠のタイムスタンプ形式を明記
Component Name別名を複数登録できるよう仕様変更
Component Dependency Relationship「依存関係」の定義を明確化(一方が他方の動作に必須な関係)
Distribution and Deliveryアクセス制御の考慮を統合しつつ、簡潔化
Frequency用語を現代的に整理(意図は不変)
削除された要素:Access Controls
2021年版で独立していた「アクセス制御」要素は廃止され、内容は「Distribution and Delivery」に統合されました。SBOM共有の実務が成熟したため、単独項目として立てる必要がなくなったためです。

⑤ まとめ:改訂の狙い

  • 検証可能性の強化 — ハッシュ値・デジタル署名により「このSBOMは本物か、コンポーネントは改ざんされていないか」を確認できるようにした。
  • ライセンス・法的リスクへの対応 — Component Licenseの新設。
  • ツール・形式の透明性 — SBOM自体がどのツール・形式・バージョン・生成タイミングで作られたかを追跡可能に。
  • 用語の明確化 — Supplier→Producer、Depth→Coverageなど、実運用で生じた曖昧さを解消。
  • 国際整合性 — EUサイバーレジリエンス法やG7のAI向けSBOMガイダンス(2026年5月発行)などと足並みを揃える方向性。
